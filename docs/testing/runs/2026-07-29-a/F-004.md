## Findings

### [S2] Bundled Onest / Geist Mono webfonts are never used — the whole UI falls back to a generic system font

- Where: `packages/ui/src/design/tokens/typography.css:2-3` vs
  `packages/ui/src/design/index.ts:8-9` (`@fontsource-variable/*`). Affects every
  surface in the app.
- Repro:
  1. Fresh state, load `http://localhost:5199`.
  2. Enumerate `@font-face` rules: the only registered families are
     `"Onest Variable"` and `"Geist Mono Variable"` (10 faces).
  3. Read the tokens: `--font-sans: "Onest",-apple-system,"Segoe UI",sans-serif` and
     `--font-mono: "Geist Mono","SF Mono",ui-monospace,monospace`.
  4. `[...document.fonts].map(f => f.family + '/' + f.status)` → all 10 faces
     `unloaded` **after** the app has fully rendered.
  5. `performance.getEntriesByType('resource')` filtered on `/woff|\.ttf/` → `[]`
     (0 of 250 resources).
  6. Width probe of the same 40px string: `var(--font-sans)` → 530.74px, while
     `"Onest"` alone → 478.62px, identical to `serif`. The token list resolves past
     `Onest` to the generic `sans-serif`.
- Expected / Actual: expected the self-hosted Onest and Geist Mono faces to be applied
  to the type ramp (FR-3's stated purpose: "Bundle the Onest and Geist Mono font files
  locally"). Actual: the family names never match — the bundled woff2 files are
  requested zero times and the chrome renders in the generic `sans-serif` /
  `monospace` fallback, which will differ per OS.
- Evidence: the upstream packages declare
  `font-family: 'Onest Variable';` (`packages/ui/node_modules/@fontsource-variable/onest/index.css`)
  and `font-family: 'Geist Mono Variable';` (geist-mono). The tokens ask for `"Onest"`
  and `"Geist Mono"`. Nothing bridges the two — the vendored `fonts.css` deliberately
  contains no `@font-face` (only the deviation comment).
- Ref: FR-3, FR-1 (Onest + Geist Mono type ramp), FR-5.
- Note: this is a font-fidelity bug, not an offline bug. Offline (FR-3) still passes —
  it passes trivially, because nothing is fetched.

### [S4] Canvas overlay/chrome colors set from JS bypass the no-hex gate

- Where: `packages/ui/src/shell/Canvas.svelte:310`
  (`ctx.fillStyle = lightMode ? '#000000' : '#ffffff'`).
- Repro: `grep -rEn '#[0-9a-fA-F]{3,8}' --include='*.svelte' packages/ui/src | grep -v src/design/`
  → 10 hits, all in script blocks (invisible to stylelint's CSS-only rule).
- Expected / Actual: per CLAUDE.md's canvas boundary rule, canvas _overlay_ colors come
  from design tokens; only _document content_ (glass, lead) is exempt. The light-mode
  backdrop fill is chrome, authored as a raw literal. The remaining hits are legitimate
  or benign: default glass colors (`GlassRenderLayer.svelte:58`, `LightLayer.svelte:54`,
  `NestView.svelte:20`, `GlassEditorDialog.svelte:49` — document data), gallery demo
  swatches, and `ImportDialog.svelte:61-62` which reads tokens with a hex fallback.
- Evidence: the spec's implementation notes already flag the gate as color-only; they do
  not mention that it is also CSS-only.
- Ref: FR-4, CLAUDE.md canvas boundary rule.

### [Q] Sidebar is 322px, not the 220px the studio kit and this spec document

- Where: `packages/ui/src/shell/ActivityRail.svelte:79` (`width: 52px`) +
  `packages/ui/src/shell/DockPanel.svelte:123` (`width: 270px`); measured 53px + 271px
  including borders.
- Expected / Actual: the spec (Scope, FR-5) says "220px left sidebar". Actual: the left
  side is a two-part rail + dock totalling 322px. This looks like an intentional
  evolution introduced by the later panel features (F-013 and on), which the spec's
  implementation notes do not record. It renders well and matches the studio _feel_;
  it just no longer matches the documented number.
- Ref: FR-5. Needs a spec decision: update F-004's number, or resize the dock.

### [Q] No dark theme — `prefers-color-scheme: dark` is ignored

- Where: whole app.
- Repro: `resize_window` with `colorScheme: dark`; screenshot; compare with light.
- Expected / Actual: the two screenshots are pixel-identical; `matchMedia('(prefers-color-scheme: dark)').matches === true` while no stylesheet contains a
  `prefers-color-scheme` media rule and `document.documentElement` has no `data-theme`.
  The app is light-only. Legibility is fine in both cases (it simply stays light), so
  this is not a rendering failure — but the design system does carry dark surfaces (the
  Toast is a dark snackbar; the spec's Toast note reasons about "nearest token on
  dark"), which suggests dark tokens exist without a theme switch.
- Ref: heuristic B (light and dark render legibly) — passes; flagged as a scope question
  since F-004 never promised a dark theme.

## First-time-user narrative

The app boots instantly into something that genuinely reads as a designed product: warm
paper chrome, a calm 56px top bar, a readiness strip that tells me where I am, and a
floating tool card that sits politely outside the rulers. Nothing is blank, nothing
overlaps, nothing scrolls that should not. Every icon I hovered had a tooltip, and the
numbers are all in mono, so it feels consistent rather than assembled.

The best moment was the token probe: 97 custom properties, not one of them unresolved,
and no raw hex anywhere in the authored CSS. That is the design-system promise actually
kept.

The worst moment was realising the typeface is a lie. The chrome looks right, but it is
being rendered by whatever generic sans the OS hands over — the bundled Onest and Geist
Mono woff2 files are never even requested, because the tokens ask for "Onest" while the
bundled faces are called "Onest Variable". A one-line fix, but until it lands, every
screenshot review and every cross-platform comparison is judging the wrong font.

## Suggested learnings

- (F-004, 2026-07-29) Font fidelity needs its own oracle: `[...document.fonts]` all
  `unloaded` plus zero `woff2` entries in `performance.getEntriesByType('resource')`
  proves a family-name mismatch that no screenshot will reveal.
- (F-004, 2026-07-29) `stylelint color-no-hex` only sees CSS — colours assigned in
  script (`ctx.fillStyle`, component defaults) need a separate grep when auditing the
  token-only rule.
- (setup, 2026-07-29) `resize_window {colorScheme}` flips the media query but this app
  is light-only, so identical light/dark screenshots are expected, not a tooling
  failure.
