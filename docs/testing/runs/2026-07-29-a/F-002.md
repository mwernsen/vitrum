## Findings

### [S2] The Cmd+K palette is a modal that neither takes focus nor traps it

- Where: debug command palette (`Dialog` primitive, `role="dialog"`, `aria-modal="true"`,
  `aria-labelledby="dialog-title"`).
- Repro (from fresh state):
  1. Press Cmd+K.
  2. Read `document.activeElement` — it is `BODY`.
  3. Press Tab three times.
  4. Focus is on the glass-library `Search glass…` input, i.e. behind the modal.
- Expected / Actual: expected focus to move into the dialog on open, cycle only among
  `Add segment` / `Undo` / `Redo` / `Load stress scene` / close, and return to the
  invoking context on Escape. Actual: focus starts outside the dialog and tabs straight
  into the obscured background; a keyboard-only user cannot reach the dialog's own
  buttons without tabbing blindly through the whole app.
- Evidence: `{"inDialog": false, "active": "INPUT", "focusVisible": true,
  "dialogAttrs": {"modal": "true", "labelled": "dialog-title"}}` after Cmd+K + 3× Tab.
- Ref: heuristic D (dialogs trap focus and restore it on close). The `Dialog` primitive is
  shared, so this very likely affects every dialog in the app (F-004 surface), not just the
  debug palette.

### [S3] "Unsaved" never clears when undo returns to the last-saved state

- Where: TopBar save badge.
- Repro: 1. draw anything; 2. Cmd+S (badge → `Saved`); 3. Cmd+Z back to the saved state
  (or, from a fresh document, edit then undo every edit).
- Expected / Actual: expected the badge to read `Saved` again once the document is
  identical to what was written; actual it stays `Unsaved` — including for a completely
  empty, never-edited-in-net document (step 9: `Segments: 0`, Undo disabled, badge
  `Unsaved`).
- Evidence: `{"palette": "… Segments: 0 …", "badge": "Unsaved", "undoDisabled": true}`.
  `DocumentStore.#commit` sets `#dirty = true` on every commit including undo, and only
  `markSaved`/`load` clear it.
- Consequence for a first-time user: New/Open will raise "Discard unsaved changes?" for a
  document that has no unsaved changes, and the badge stops being trustworthy.
- Ref: Scope "Dirty-state tracking and unsaved-changes warning".

### [S3] The chrome shows a title that is not the document — and no filename after saving

- Where: TopBar document title, next to the save badge.
- Repro: fresh app → title reads `Sample panel`; decode `vitrum:autosave` →
  `project.settings.name` is `"Untitled"`; press Cmd+S → the suggested file is
  `Untitled.vitrum` while the title still reads `Sample panel`.
- Expected / Actual: for a story about "my project is a file I own", expected the title to
  be the document name and, after a save, to reflect the file. Actual: a hardcoded
  placeholder unrelated to the document, and no path or filename displayed anywhere.
- Evidence: header `innerText` = `Vitrum | Sample panel | Saved | …`; autosave
  `document.json` → `settings.name: "Untitled"`.
- Ref: FR-3/FR-6 story framing; heuristic G (terminology consistent across surfaces).

### [S3] Undo/redo tooltips omit their keyboard shortcuts

- Where: TopBar icon buttons.
- Repro: hover Undo / Redo.
- Expected / Actual: the tool buttons set the convention (`Line (L)`, `Select (Esc)`);
  expected `Undo (⌘Z)` / `Redo (⇧⌘Z)`. Actual `title="Undo"` / `title="Redo"` — the two
  shortcuts the spec explicitly wires are never surfaced.
- Evidence: `<button class="icon-btn" aria-label="Undo" title="Undo">`.
- Ref: heuristic A (icon-only control tooltips name the shortcut where one exists).

### [S3] Nothing on screen offers, or even hints at, save / open / new

- Where: whole shell (browser host).
- Repro: look for any way to save without knowing Cmd+S.
- Expected / Actual: the spec deliberately limits this to the native menu, which the
  browser host does not have; but the `Unsaved` badge is inert text and no tooltip,
  status-bar hint or empty-state copy mentions Cmd+S / Cmd+O. A first-time user in this
  build cannot discover that the document can be saved at all.
- Evidence: full `read_page` interactive tree contains no save/open/new control.
- Ref: spec non-goals (menu-only is intended) + heuristic A. Filed as discoverability, not
  as an FR violation; worth a decision on whether the badge should be the save button.

### [S3] TopBar and Inspector are clipped at narrow widths with no overflow affordance

- Where: shell layout at 820×1000 (checked 1280×800 ✓, 1050×700 ✓, 820×1000 ✗).
- Repro: resize to 820×1000.
- Expected / Actual: expected controls to collapse, wrap or scroll. Actual `Zoom to fit`,
  `Import SVG`, `Export` and the avatar sit beyond the right edge, the Inspector's right
  half (Start y / End y / Angle, `Rotate 90°`) is cut, `tackle in any order` truncates to
  `tackl`, and the page does not scroll — the controls are simply unreachable. The document
  title also wraps to two lines inside the 56px bar.
- Evidence: `pageScrollW == innerW == 820` while clipped elements report
  `right > innerWidth`: `["Zoom to fit","Import SVG","Export (SVG, PDF, DXF)","MK"]`;
  inspector `right = 939`.
- Ref: heuristic B. Undo/redo and the save badge — F-002's own controls — survive at this
  width, so this is shell-level (F-001/F-004) rather than F-002-specific.

### [S4] Two different controls share the accessible name "Zoom to fit"

- Where: TopBar (`ref_9`) and StatusBar (`ref_60`).
- Repro: `read_page` → both appear as `button "Zoom to fit"`.
- Expected / Actual: role + name should identify one control (the Electron E2E suite locates
  everything that way). Actual: an ambiguous locator, and a duplicated affordance in two
  places with no visible relationship.
- Ref: heuristic D (targetable by role + name) / B (no duplicated controls).

### [S4] Saving is silent beyond the badge flip

- Where: Cmd+S.
- Expected / Actual: expected some confirmation naming the file. Actual: the badge changes
  and nothing else — in the browser host the file is downloaded silently, and
  `StoragePort.saveFile` ignores the path and always writes `design.vitrum` (dev stub, so
  the in-place-save semantics resolved in open question 2 cannot be observed here).
- Ref: heuristic C (actions give feedback).

### [Q] No dark theme

`resize_window colorScheme: dark` still renders the warm-paper light theme. Everything
remains legible, so this is recorded as an intentional-looking deviation from heuristic B
rather than a defect — confirm that a dark theme is out of scope for the design system.

## Not testable in this environment

- **Open (`Cmd+O`)** — native `<input type=file>` picker; browser-host stub. Not triggered.
- **Save / Save-as file content** — anchor download; the keystroke and its state effects
  were exercised (step 14), the produced `.vitrum` bytes cannot be inspected. Save-as
  (`Cmd+Shift+S`) not triggered to avoid a second download.
- **Crash-recovery prompt (FR-5 second half)** — `window.confirm("Recover unsaved work…")`
  plus a reload while dirty; per the environment dossier this wedges the Browser pane and
  can take the shared dev server down. Verified indirectly: an autosave snapshot exists
  exactly while the document is dirty and is cleared on save.
- **Unsaved-changes guard on close / New / Open** — `beforeunload` and
  `window.confirm("Discard unsaved changes?")`, both native.
- **Native File/Edit menu wiring (`new`, `open`, `save`, `saveAs`, `undo`, `redo`,
  `togglePalette`)** — Electron main process only; the browser host has no menu.
- **Migration + newer-`schemaVersion` rejection (FR-4), command immutability (FR-1)** —
  non-UI, covered by the package's unit/property tests.
- **Inspector numeric-field edit as a single undo entry** — attempted; the browser typing
  tool was unavailable (three attempts). Retest next run.

## First-time-user narrative

The undo story is the best part of this build and it is genuinely convincing: a two-segment
polyline drawn in one gesture disappears with a single Cmd+Z, a node drag collapses to one
entry, and undoing five steps then redoing them gives back a byte-identical document — I
checked the packed bytes, not just the counts. That is the "experiment fearlessly" half of
the promise, and it holds.

The "a file I own" half is where I got lost. The chrome tells me I am editing "Sample
panel", the file it would write is "Untitled.vitrum", and after Cmd+S nothing tells me where
anything went — the badge just goes quiet. I only knew Cmd+S existed because the spec told
me; nothing on screen mentions saving. The worst moment was watching the badge keep saying
`Unsaved` after I had undone my way back to an empty document: the one indicator I am asked
to trust was telling me I had work to lose when I had none. The second-worst was Cmd+K: a
modal opens, my keyboard focus stays outside it, and three Tabs later I am typing into the
glass search box behind the dialog.

## Suggested learnings

- (F-002, 2026-07-29) In this Browser pane, `computer` coordinates are ~CSS ÷ 2.075 at
  1280×800, and `ref`-based clicks are mis-scaled the same way (a ref click on the Line tool
  landed on the canvas). Derive the factor once per viewport by hovering a point and reading
  `clientX/clientY` from a temporary `mousemove` listener, then click with CSS ÷ factor.
- (F-002, 2026-07-29) The line tool is a chained polyline: click A, **move**, then
  double-click B. Without an intervening `hover` the gesture never starts — two silent
  no-op attempts looked like a product bug but were an automation artefact.
- (F-002, 2026-07-29) `vitrum:autosave` can be decoded in-page with
  `DecompressionStream('deflate-raw')` over the local-file-header walk; comparing
  `document.json` strings before/after undo-all → redo-all is a precise FR-2 oracle. Allow
  ~6 s for the throttled snapshot to catch up.
- (F-002, 2026-07-29) `DocumentStore` marks the document dirty on undo/redo too, so the
  `Unsaved` badge never returns to `Saved` — expect this in every feature that reads the
  badge as an oracle.
