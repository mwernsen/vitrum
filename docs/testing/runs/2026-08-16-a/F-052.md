# F-052 Live symmetry — user test report

Run: docs/testing/runs/2026-08-16-a · Mode: exploratory (manual, Mathieu) · Verdict: fail

## Provenance

Not a scripted browser pass. Mathieu ran an unstructured first-user session — reproducing an
existing real window (a Dutch Art Deco transom: nested yellow/orange border with red corner
squares, plus an interlaced two-ring motif) — and got stuck at setup. Each finding below was
then confirmed by reading the source; no finding rests on the photo alone.

## Story attempted

Spec's signature promise: "Draw one half (or one wedge) and see the whole design mirror live."

1. ✓ Created a panel via the new-panel dialog (size + technique).
2. ✓ Found the symmetry controls in the Draw dock section (mode grid, axis angle, fold count,
   add mirror, bake).
3. ✗ Could not place the symmetry centre anywhere useful — see finding 1. The story stops here:
   with the centre on the panel's corner, "draw one half" produces replicas outside the glass.
4. — Not reached: drawing a sector, bake, glass assignment across sectors.

## Findings

### [S1] The symmetry centre is pinned to the panel's top-left corner and cannot be moved

- Where: Draw dock → Symmetry; `SymmetryController` / `AppShell`.
- Repro: create any panel, set mode to `mirror` (or `double mirror`, or `radial`). The axes
  and the shaded source domain anchor on world (0, 0), which is the panel's top-left corner.
  Every replica lands outside the panel.
- Cause: `defaultCenter: () => vec2(0, 0)` ([AppShell.svelte:176](../../../packages/ui/src/shell/AppShell.svelte:176)),
  while the panel rectangle spans (0, 0)→(width, height)
  ([scene.ts:34](../../../packages/ui/src/canvas/scene.ts:34)). The origin is the panel's
  corner, not its centre.
- Aggravating: there is no way to correct it. `SymmetryController.setCenter`
  ([symmetry.svelte.ts:142](../../../packages/ui/src/tools/symmetry.svelte.ts:142)) exists but
  has no caller in the UI — `DrawPanel.svelte` exposes only angle, fold count, mirror and
  bake, and on-canvas centre dragging is still an open follow-up in the spec.
- Expected: the centre seeds to the panel's centre, and is editable (numeric fields at
  minimum, on-canvas handle ideally).
- Note: the spec records the (0, 0) default as a deliberate decision — "the predictable pivot
  a user expects, and where the grid axes already cross" (Implementation notes,
  2026-07-22). That reasoning holds only for an origin-centred document; it does not survive
  panels being laid out from the origin. Worth re-deciding rather than treating as settled.
- Ref: FR-5 is satisfied in the mechanical sense (pointers do fold into the source), but the
  spec's core story cannot complete on a real panel.

### [S2] Symmetry replicates linework only — glass assignment is per-sector manual work

- Where: symmetry expansion vs. F-023 glass assignment.
- Repro (by inspection): assignments key off a piece's content id, which hashes the ring's
  absolute coordinates ([identity.ts:28](../../../packages/core/src/pieces/identity.ts:28)).
  A replica piece sits at different coordinates, so it hashes to a different key and carries
  no glass.
- Effect: on a 4-fold border the user paints the same colour pattern four times. For designs
  where the colour placement _is_ the symmetry — the tested window is exactly that — most of
  the feature's leverage is lost.
- Expected: at minimum an option for a replica piece to inherit its source piece's glass.
- Ref: not an FR violation (the spec scopes replication to geometry), so this is a design gap,
  not a bug. It changes assignment key semantics and touches saved files, so it needs
  Mathieu's decision before implementation, not a fix ticket.

### [S2] Snapping is evaluated in folded source space, so drawing across the axis flips between 45° angles

- Where: [AppShell.svelte:180](../../../packages/ui/src/shell/AppShell.svelte:180)
  (`snap.resolver(symmetry.canonicalize(world), ctx)`) and
  [AppShell.svelte:258](../../../packages/ui/src/shell/AppShell.svelte:258)
  (`snap.updateScene(shownSegments)`).
- Repro (Mathieu, observed): with symmetry on, start a line and move the cursor across the
  symmetry axis. The preview jumps between 45° angles instead of following the cursor.
- Cause, in two halves:
  1. **The snap index holds source segments only** — `updateScene(shownSegments)`, whose comment
     states the intent: "Snapping stays over the _source_ only (replicas are read-only)." So with
     the cursor in a replica sector there is no geometry under it to snap to. The only kinds that
     can still fire are the two that need no targets: grid and angle.
  2. **Angle snap is then measured against a reflected point.** `snapAngle`
     ([snap.ts:262](../../../packages/core/src/snap/snap.ts:262)) fans 8 rays at multiples of
     `ANGLE_STEP = Math.PI / 4` ([snap.ts:71](../../../packages/core/src/snap/snap.ts:71)) from
     the last placed anchor and captures by perpendicular distance. Because the point reaching it
     has already been folded, near the axis it barely moves (several rays inside the radius at
     once) and crossing the axis reverses its direction of travel (it sweeps back over those rays,
     each winning in turn).
     So the 45° flipping is not a coincidence of the fold — angle snap is the _only_ live snap kind
     out there, and it is the one kind that is direction-sensitive.
- Also: snap guides come back in source space, so the markers the user sees are nowhere near their
  cursor.
- Aggravated by finding 1: with the default axis (angle 90°, centre (0, 0)) the source half-plane
  is `x ≤ 0`, so the **whole panel** sits on the replica side and every stroke is folded. The
  pathological case is the normal case today.
- Ref: the spec calls the fold-then-snap order a deliberate "one-line composition at the F-011 /
  F-012 resolver seam" (Decision §1), chosen to avoid touching tool contracts. That holds for
  pointer confinement; it does not survive a direction-sensitive snap kind, and pairing it with a
  source-only snap index leaves the replica sectors with exactly the wrong subset of snapping.
- Fix: **snap in the sector the cursor is in, then fold the winner back to source.**
  1. Expose the sector index `k` — `canonicalizeToSource` already computes it
     ([canonicalize.ts:36](../../../packages/core/src/symmetry/canonicalize.ts:36)) and discards it.
  2. Build the snap scene over the **expanded** network (`DocumentController.replicaNetwork()`
     already exists) so replica geometry is snappable.
  3. Map the gesture's anchors into sector `k` before angle snap.
  4. Apply transform `k⁻¹` to the winning point to get the source coordinate.
     This is exact, not a compromise: replicas are rigid images, so snapping to replica `k`'s
     endpoint and applying `k⁻¹` lands precisely on the source endpoint. An earlier reading of this
     finding worried that a snapped point "loses its snap" through the fold — that was measuring the
     wrong space. The line is at 45° **in the sector the user drew it in**, which is what they asked
     for; its source twin sitting at the reflected angle is correct.
- Costs, both accepted: grid-snapped points yield off-grid _source_ coordinates when the axis is
  not a multiple of 45° through a grid node (the design is right, the stored numbers are untidy);
  and the change is larger than Decision §1's one-line composition — roughly half a day with tests.
- Bonus: the user gains snapping **to** replica geometry, which the tested window needs (the border
  quarter must meet its own mirror image cleanly).

### [S3] One document-wide setup cannot express a design with nested symmetries

- Where: `Project.symmetry` (Decision §2 — one setup per document).
- The tested window has a border that is mirror-symmetric on both axes (D2) and a centre motif
  that is only 180°-rotational (C2). Both are individually supported (`double mirror`,
  `radial` fold 2), but not simultaneously.
- Workaround that does work: stage it with bake — `double mirror`, draw a quarter of the
  border, **bake**; then `radial` fold 2, draw half the motif, **bake**; then mode off for
  asymmetric details.
- Expected: nothing in the UI suggests bake is the staging tool. Its label reads as a one-way
  commit, so a first-time user reads "my design doesn't fit any option" instead of "bake
  between stages". A hint line, or per-region symmetry, would close this.

### [Q] "Radial fold 2" is the only way to ask for a 180° rotation

- The mode grid offers `mirror` / `double mirror` / `radial N-fold`. Plain 2-fold rotation —
  extremely common in domestic transoms and Art Deco panels — is reachable only as radial with
  count 2 and mirror off, which is not discoverable from the glyphs (`◧ ⊞ ✳`).
- Question for the spec: is a named "rotate 180°" preset worth a fourth mode, or a preset row?

## Not reached

Drawing inside a sector, live replica preview, bake round-trip, seam coherence, DRC and BOM
over the expanded network — all blocked by finding 1.
